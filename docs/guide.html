01Overview & Problem Statement

Most software teams have a growing gap between the people who write code and the people who own the business. Developers understand what the system does technically; stakeholders understand what the business needs. Bridging that gap traditionally requires hours of manual documentation, time-consuming code reviews, or dedicated business analyst effort.

Customer Insights closes that gap instantly. It connects directly to a GitHub organisation, reads the actual source code of any repository, and uses an AI language model to answer questions in plain English — no technical background required.

In one sentence
Point it at a GitHub repository. Ask a question in plain English. Get a business-level answer in seconds.

The tool is a zero-dependency, browser-based application. It requires no server, no build pipeline, no database, and no installed software beyond a modern browser. It can also be packaged as a Java WAR file and deployed to any Java application server (Tomcat, JBoss, WebLogic, WebSphere) for team-wide access.

02Why It Was Built

The idea emerged from a recurring frustration: when onboarding onto a new project or reviewing a customer's implementation, the fastest way to understand what a system does is to ask someone who built it. But that person is often unavailable, no longer on the team, or the code has evolved beyond their memory.

Existing alternatives all had significant barriers:

  • Custom GPT integrations — required API access setup that was difficult to approve and demo within organisation security constraints.
  • MCP (Model Context Protocol) tools — too technical to hand to a non-developer audience; required local tooling.
  • Manual documentation — always out of date; rarely reflected the actual running code.
  • Code review sessions — time-intensive; required a developer in the room.

The goal was to build something that a project manager, a solutions consultant, or a business analyst could pick up and use immediately — with nothing installed, no setup beyond entering an API key, and answers in the language they already use.

Core principle The code is the documentation. Rather than maintaining a parallel knowledge base that drifts from reality, this tool reads the live source and derives understanding on demand.

03Use Cases

Use Case 1 — Customer Onboarding

Who: Solutions consultant, implementation engineer, or account manager joining a project mid-flight.

Situation: A customer's implementation has dozens of customised files built over several years. There is no handover document.

Action: Select the customer's repository → ask "What does this customer's system do?" → receive a structured business-level summary in under 30 seconds.

Use Case 2 — Non-Technical Stakeholder Q&A

Who: Product owner, delivery manager, or C-level sponsor who needs to understand what was delivered.

Situation: A stakeholder asks "Does our system send automated reminders?" or "What happens when an invoice is approved?"

Action: Translate Script mode → paste or describe the relevant area → get a plain-English explanation with no technical jargon.

Use Case 3 — Cross-Customer Feature Audit

Who: Product team deciding which features to standardise or productise.

Situation: The team wants to know which customers have built automated invoicing, multi-currency support, or scheduled batch jobs.

Action: Feature Search mode → enter the capability → the tool scans up to 50 repositories and identifies which customers have it and how they've implemented it.

Use Case 4 — Competitive / Portfolio Comparison

Who: Delivery director or architect reviewing consistency across customer implementations.

Situation: Two customers both run the same platform but have diverged significantly in their configuration and customisation.

Action: Cross-Customer Compare mode → select both repositories → ask "How does their business logic differ?" → receive a structured side-by-side comparison.

Use Case 5 — Knowledge Retention

Who: Team lead or architect during a team transition.

Situation: A senior developer who owns all the institutional knowledge about a customer is leaving the team.

Action: Run a full summary of the repository before they leave. Use follow-up chat to ask about specific modules. Export the result to preserve institutional knowledge.

Use Case 6 — Pre-Sales / Demo Preparation

Who: Pre-sales engineer or consultant preparing for a customer call.

Situation: 30 minutes before a call and no time for a deep-dive code review.

Action: Quick summary → key business processes → integrations used → walk into the meeting prepared.

Interaction Features

  • Streaming responses — answers appear word-by-word in real time; no waiting for the full response
  • Follow-up chat — ask clarifying questions on any result without re-fetching the code; full conversation history maintained per card
  • Quick prompts — one-click pre-built questions tailored to each mode
  • Copy to clipboard — single button copies the full markdown text of any result
  • Result history — last 20 results survive page refresh; stored in browser localStorage
  • Token usage badge — shows input/output token counts per query for cost tracking

Repository Handling

  • Priority file selection — automatically focuses on business-logic files (.java, .py, .js, .ts, .sql, config, rules) before low-value files
  • Skip list — ignores node_modules, minified files, lock files, binary assets automatically
  • Path filter — narrow the file scan to a specific folder (e.g. src/business/)
  • 5,000-character cap per file — large files are truncated at the most relevant section
  • Pagination support — loads all pages of repositories from GitHub (handles orgs with 100+ repos)
  • Org and personal account — auto-detects whether the GitHub user is an org or personal account
  • Failed file reporting — if individual files can't be read, they are listed in the result rather than silently skipped

Resilience

  • Retry with backoff — failed GitHub API calls retry up to 2 times (800ms / 1600ms delay)
  • Rate limit indicator — header badge shows remaining GitHub API quota; warns at <100, critical at <10
  • Rate limit error handling — throws a clear, timed error message when quota is exhausted (403/429)

Multi-LLM Support

  • Anthropic Claude — native Messages API with SSE streaming
  • OpenAI GPT — Chat Completions API with SSE streaming
  • Any OpenAI-compatible provider — Groq, Ollama, Azure OpenAI, LM Studio, or any endpoint with a custom base URL
  • Configurable model name — full control over which model variant to use

Configuration

  • localStorage persistence — config survives page refresh
  • Server-side config.json — pre-populate credentials for team deployments
  • Collapsible config panel — auto-collapses after loading repos to maximise working area

05Technical Architecture

Browser │ ├── index.html — App shell, layout, config UI ├── css/styles.css — All styling (design system tokens, responsive) └── js/app.js — All application logic │ ├── ConfigManager — Reads/writes localStorage + config.json │ Manages provider, model, API key, GitHub creds │ ├── GitHubClient — GitHub REST API v3 calls │ ├── loadRepos() GET /orgs/:org/repos (paginated) │ ├── fetchRepoFiles() GET /repos/:org/:repo/git/trees/HEAD │ │ GET /repos/:org/:repo/contents/:path │ ├── fetchWithRetry() Exponential backoff wrapper │ └── checkRateLimit() X-RateLimit-* header parser │ ├── LLMClient — AI provider abstraction │ └── ask() SSE streaming for Anthropic + OpenAI │ ├── ResultCard — Self-contained result card DOM component │ ├── beginStreaming() Pre-wrap live text display │ ├── update() Renders markdown via DOMPurify + marked.js │ ├── showTokenBadge() Token usage display │ └── copy() Clipboard write │ └── App — Orchestrator ├── Modes: summarise / translate / feature / compare ├── Follow-up chat (multi-turn conversation history per card) ├── Result persistence (localStorage, 20-result cap) └── Event delegation (repo list clicks, no inline user-data handlers) External APIs (browser → API, no server proxy) ├── api.github.com — Repository tree + file contents ├── api.anthropic.com — Claude models (streaming) └── api.openai.com — GPT models (streaming) or custom base URL — Groq, Azure, Ollama, etc.

Data Flow

  1. User selects a repository from the sidebar. The app fetches the file tree from GitHub's Git Trees API.
  2. Files are ranked by relevance (business logic files first) and the top N are fetched concurrently via the Contents API. Each file is decoded from base64 and capped at 5,000 characters.
  3. A structured prompt is assembled: system prompt (role + instructions) + user message (repository name + file contents + the user's question).
  4. The prompt is sent to the configured AI provider via its streaming API. The response streams back as Server-Sent Events.
  5. The app parses SSE deltas in real time and renders them live in the result card. On completion, the full text is sanitised with DOMPurify and rendered as rich markdown.
No server required All API calls are made directly from the browser. There is no backend, no proxy, and no database. The only server needed is a static file host (or Java application server for WAR deployment).

06Quick Start (Browser)

  1. Open index.html in a modern browser (Chrome, Edge, Firefox, Safari). If running from the filesystem, some browsers may block API calls — use a local server or the WAR deployment instead.
  2. In the Configuration panel, select your AI provider (Anthropic, OpenAI, or Custom).
  3. Enter your AI API key and optionally specify a model name (defaults are provided per provider).
  4. Enter your GitHub Personal Access Token and your GitHub organisation or username.
  5. Click Load Repositories. The sidebar populates with all repositories.
  6. Select a mode tab (Summarise, Translate, Feature Search, or Compare).
  7. Select a repository (or multiple for Compare), type a question or click a quick prompt, then click Ask.

GitHub Token Requirements

The token needs read access to repository contents and metadata. For a classic token, enable the repo scope (or read:org + contents:read for fine-grained tokens).

Note on CORS The GitHub API and AI provider APIs all support browser-direct access (CORS headers are present). Anthropic requires the anthropic-dangerous-direct-browser-access: true header, which this app sends automatically.

Step-by-Step: Package and Deploy

  1. Clone the repository 
    git clone https://github.com/mohit1jindal/customer-insights.git
cd customer-insights
  2. Create your config.json (optional — enables pre-populated credentials for the whole team) 
    cp config.sample.json config.json
    Edit config.json and fill in the values: 
    {
  "anthropicKey": "sk-ant-...",
  "githubToken":  "ghp_...",
  "githubOrg":    "your-org-name",
  "provider":     "anthropic",
  "model":        "claude-sonnet-4-20250514"
}
    Security warning Never commit config.json to git. It contains API credentials. The file is listed in .gitignore.
  3. Package as a WAR 
    # From the repo root directory
jar -cvf customer-insights.war *
    Or with Maven (if using a pom.xml wrapper): 
    mvn package
  4. Deploy to Apache Tomcat 
    # Copy WAR to Tomcat's webapps directory
cp customer-insights.war $CATALINA_HOME/webapps/

# Start or reload Tomcat
$CATALINA_HOME/bin/startup.sh
    Tomcat automatically unpacks the WAR. The app is then available at: 
    http://<server>:8080/customer-insights/
  5. Deploy to JBoss / WildFly 
    cp customer-insights.war $JBOSS_HOME/standalone/deployments/
    JBoss hot-deploys on file copy. Access at: 
    http://<server>:8080/customer-insights/
  6. Deploy to WebLogic Use the WebLogic Administration Console → Deployments → Install → upload the WAR file. Set the context root to /customer-insights.
  7. Deploy to WebSphere In the WebSphere Administration Console: Applications → New Application → New Enterprise Application → upload WAR → set context root to /customer-insights.

Reverse Proxy (Nginx)

For production use, place Nginx in front of Tomcat to handle TLS:

server {
    listen 443 ssl;
    server_name insights.yourcompany.com;
    ssl_certificate     /etc/ssl/certs/your-cert.crt;
    ssl_certificate_key /etc/ssl/private/your-key.key;

    location /customer-insights/ {
        proxy_pass http://127.0.0.1:8080/customer-insights/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
HTTPS requirement The navigator.clipboard API (used by the Copy button) requires HTTPS. In production, always deploy behind TLS.

09Security Considerations

Fixes Applied in v5

IssueRiskFix
Repo names injected raw into innerHTML and onclick XSS — a maliciously named repo could inject scripts All user-derived strings passed through escapeHtml() before HTML insertion. Repo list uses event delegation + data-repo attributes instead of inline onclick with user data.
LLM output rendered via marked.parse() directly into innerHTML XSS — if the LLM returns <script> or crafted HTML in its response All markdown output is passed through DOMPurify.sanitize() before being set as innerHTML.
GitHub API error messages injected into innerHTML XSS — API error body could contain HTML escapeHtml(e.message) applied before all DOM insertion.
GitHub API URLs constructed without encoding Path injection — org/repo names with special characters could alter API endpoint All dynamic URL segments wrapped in encodeURIComponent().

API Key Handling

  • Keys are stored in browser localStorage — scoped to the origin, not sent anywhere except the intended API endpoints.
  • Keys are never logged, never sent to any third-party service, and never appear in URLs.
  • For server deployments using config.json: ensure the file is not accessible publicly if deployed on a shared or internet-facing server. Use Nginx/Apache rules to block direct access to config.json.
  • Recommended: use a dedicated read-only GitHub token scoped to specific repositories.

Blocking config.json in Nginx

location = /customer-insights/config.json {
    deny all;
    return 403;
}

Content Security Policy (Recommended)

Content-Security-Policy:
  default-src 'self';
  script-src 'self' https://cdn.jsdelivr.net;
  connect-src 'self'
              https://api.github.com
              https://api.anthropic.com
              https://api.openai.com;
  style-src 'self' https://fonts.googleapis.com;
  font-src https://fonts.gstatic.com;

HTTPS

Always deploy behind HTTPS in production. The navigator.clipboard API, secure cookies, and some browser security policies require a secure context.

10Object-Oriented Design

Version 5 refactored the entire application from a flat procedural script into a class-based architecture with clear separation of concerns.

Class Hierarchy

ClassResponsibilityKey methods
ConfigManager Encapsulates all configuration state: reading/writing localStorage, loading config.json, managing the config panel UI, and exposing provider/key/model as typed getters. save(), load(), loadFromServer(), onProviderChange(), togglePanel(), setStatus()
GitHubClient All GitHub REST API communication. Handles authentication headers, pagination, rate limit monitoring, retry logic, and file content decoding. No UI logic. loadRepos(), fetchRepoFiles(), fetchWithRetry(), checkRateLimit()
LLMClient AI provider abstraction. Handles both Anthropic and OpenAI streaming protocols (SSE), parses token usage, and exposes a single unified ask() interface regardless of provider. ask(systemPrompt, messages, onChunk, onComplete)
ResultCard Self-contained DOM component for a single query result. Owns its own element creation, streaming state, markdown rendering, token badge, copy functionality, and serialisation for persistence. beginStreaming(), update(), showTokenBadge(), copy(), toJSON()
App Top-level orchestrator. Holds application state (selected repo, mode, compare set, card registry). Coordinates GitHubClient → LLMClient → ResultCard pipelines. Manages event delegation and localStorage persistence. init(), runQuery(), sendFollowUp(), loadRepos(), setMode(), clearHistory()

OOP Principles Applied

  • Single Responsibility — each class has one clear job. GitHubClient doesn't know about markdown; LLMClient doesn't know about GitHub.
  • Encapsulation — internal helpers are prefixed with _ (e.g. _renderRepoList, _setBusy). State (_allRepos, _cards) is held on the instance, not in global variables.
  • Composition over inheritance — App owns instances of ConfigManager, GitHubClient, and LLMClient, delegating to each rather than extending them.
  • Dependency injection — GitHubClient and LLMClient both receive a ConfigManager reference at construction time, making their configuration source explicit and testable.
  • Thin global shims — HTML onclick attributes call single-line global wrapper functions (e.g. function runQuery() { app.runQuery(); }) that delegate immediately to the class. This keeps all business logic inside the class hierarchy.

11Known Limitations

LimitationDetailWorkaround
File cap per query Reads at most 15–20 files per repository per query (ranked by relevance). Very large or unusual code structures may miss important files. Use the Path Filter to focus on a specific folder, reducing noise and surfacing the right files.
Character cap per file Each file is truncated at 5,000 characters. Very large files (e.g. a single 10,000-line monolith) are partially read. Split large files into modules, or use the path filter to target the most relevant section.
Binary and generated files Images, PDFs, compiled outputs, and minified files are automatically skipped. Configuration stored in binary formats (e.g. encrypted property files) cannot be read. Ensure configuration is stored in text-based formats (YAML, JSON, properties).
GitHub API rate limits The unauthenticated limit is 60 req/hr; authenticated is 5,000 req/hr. Feature Search across 50 repos can consume ~150–500 requests depending on repo size. Monitor the rate limit indicator in the header. Use a dedicated service account token for team deployments.
No branch selection Always reads from the default branch (HEAD). Feature branches or release branches are not accessible. Merge changes to main before querying, or manually change the HEAD reference.
Context window limits Very large multi-repo comparisons may approach LLM context limits (especially with smaller models). Quality degrades as context fills. Use compare mode with 2–3 repositories at a time rather than many simultaneously.
No offline support Requires live internet access for GitHub API and LLM API calls. No caching of repository content. N/A — by design. Use a self-hosted Ollama endpoint if operating in a restricted network.
No authentication / authorisation When deployed as a WAR with config.json, any user who can reach the URL can use the pre-configured credentials. Deploy behind SSO/VPN, or leave config.json empty and require each user to supply their own credentials.
